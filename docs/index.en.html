01Integration principles, architecture, and inputs#

Three hard rules, the responsibility boundary between Host, App and companion APK, and the inputs to prepare before you start.

Integration principles#

Get the complete inventory first, then implement item by item; every step has a re-runnable check.

1 · Inventory first

Scan the source, get the mount points

Scan the slots, entries, and components the plugin registers plus its data dependencies, and produce an actionable report.

2 · Then implement

Pick the container by shape

Use PageContent for a full page and SlotContribution for an embedded position; data flows through PluginRpcHost, interactions through dispatchEvent.

3 · Re-runnable

2/2 slots verifiable

Re-run --check after finishing each slot; both Demo plugin slots are mapped, hosted, and companion-implemented, so they can be regressed anytime.

Best practice

Coverage first, pixels later: let the inventory drive implementation and use screenshots only for visual acceptance.

Overall architecture#

Five steps: plugin source → scan → UI inventory → native implementation → verification.

Host side

Plugin logic stays untouched

RPC, state, model calls and data queries stay in the JS plugin; native reads display data only through RPC.

App side

Slot hosts and capability bridges

Each position is hosted by NativeSlotHost / OfficialSlot; PluginRpcHost and PluginModelHost provide controlled capabilities.

All you need is your published plugin package or source repo; the scanner reads that input directly.

The scanner reads the plugin's registration info; the built-in slot list comes from the App's NativeSlotMapping.

Package name convention (mandatory)

Companion APKs always use com.dsh.mobile.<full plugin name>: keep the dsh-plugin- prefix, lower-case it, and turn non-alphanumeric characters into _. The package name derives directly from the full plugin name: dsh-plugin-demo → com.dsh.mobile.dsh_plugin_demo.

02Scan and report#

Use the SDK scanner to extract the plugin's UI inventory, RPC and gaps, then read the report correctly.

Scan the plugin source#

One scan yields every UI mount point in the plugin and the data each one needs.

your-plugin/ ├─ package.json name / version / dependencies ├─ lib/ │ ├─ client.js compiled output (fallback) │ └─ client.js.map sourcesContent holds original TSX (preferred) ├─ src/ dev repo source (secondary) │ ├─ client/index.ts │ ├─ client/DemoDockChip.tsx │ └─ client/DemoSettingsSection.tsx └─ locale/*.json string tables

What the scanner detects

Mount points

ctx.slots.register({ name, id, order, mode }, Component); slots.inject / children relationships are detected too.

Data dependencies

useProjection('...'), useChat/useSession, the inject face, and plugin RPC method names.

UI structure

The component JSX tree, visible copy, button actions, locale keys; used to confirm empty states, forms, and hint copy are all covered.

Placement / interaction

useAnchoredPosition, createPortal, anchorRef, role="dialog", side/align and other anchoring clues; if the companion uses a centered Dialog where the plugin anchors a popover, the mismatch is reported.

Gaps

Unmapped slots, missing host NativeSlot, and a passed --companion that never registers the matching contribution are all reported.

Example command: Demo plugin

python tools/plugin_ui_scanner.py \
  --plugin demo/js \
  --companion demo/native/src/main/kotlin \
  --json docs/plugin-ui-inventory-example.json \
  --check

The scan finds 2 slots (settings.section, conversation.composer.dock); both are mapped, hosted, and companion-implemented, so --check passes. The report's "RPC endpoints" are the data dependencies the Web component actually calls (demo.status / demo.bump); the full Host-side contract has 4 more endpoints.

Adding host capabilities

When a companion needs App capabilities such as "switch model" or "write file", add an optional SDK interface (see PluginRpcHost / PluginModelHost) and let the host inject it centrally.

Host capabilities and data contract#

Native reads display data from the Host only through RPC; networking and credentials stay in the Host, and the App injects capabilities.

PluginRpcHost

Call the plugin's existing RPC

rpc.callRpc(
  "demo.status",
  JsonObject(emptyMap())
) { result -> ... }
PluginModelHost

Switch model / reasoning

host.selectModel(
  provider = "your-provider",
  model = "your-model",
  reasoningEffort = "highspeed"
)
spec

App → slot state

The slot spec carries display/selection state only, for example modelId, reasoningEffort, provider, displayName.

Updates

refresh / polling

Long-running logic stays in the Host; native polls every 60s or waits for client/refresh; business state stays in the Host and native reads it on demand.

Credential boundary

Tokens / API keys / arbitrary file paths appear only in the Host; native receives display data only.

05Validation, launch checks, and operating notes#

The full loop from --check to on-device acceptance, plus the order for handling common problems.

Validation and CI#

Three gates: plugin coverage, built-in slot coverage, and App unit tests.

Gate 1

plugin scanner --check

Passes when every plugin slot is mapped, hosted, and implemented by the companion.

Gate 2

slot_inventory.py

Keeps built-in slot mappings and hosts consistent; when adding a built-in slot, update mapping, host, and tests together.

Gate 3

SlotCoverageTest

Kotlin reflection asserts the full set of built-in constants; CI matches local.

# Plugin coverage (SDK repo)
python tools/plugin_ui_scanner.py --plugin <plugin> --companion <src> --check

# App-side built-in slot coverage: slot_inventory.py + SlotCoverageTest
Coverage rule

When adding a built-in slot, add the mapping, host, and tests first, then update the inventory; keep --check green on every change.

Launch checklist#

Go module by module; each item gives the right approach and the acceptance criteria.

Slot

Bridge capabilities first

A slot contribution gets only the base PluginHostApi by default; when you need RPC/model capabilities, wrap it with SlotBridgeHost before reading them.

Async loading

Make slots observable

SlotRegistry keeps an observable revision; containers recompose automatically after APK load/unload.

Loading

Use packageContext.classLoader

With multi-dex, prefer packageContext.classLoader; on a load failure, log it and degrade to Web.

Data

Backoff retry + periodic refresh

Retry with backoff while the first screen is not ready (800ms / 2s); afterwards re-read every 30–60s or on client/refresh.

Placement

Anchor popups and cap width

Use PluginPopover with width IntrinsicSize.Max, capped at 320dp.

Styling

Take all material from the theme

Overlay background, border, radius, and text come from PluginTheme's popup fields, matching the App menus.

Full checklist

See docs/pitfalls.md for each module's best practices, checks, and acceptance criteria.

Operating notes#

Do scanning, claiming, and verification in this order.

Confirm the scan input

Provide lib/client.js.map or src/*.tsx in the plugin package; if only compiled output exists, fall back to lib/client.js. Point --plugin at the package root.

Claim unmapped slots

Add the DshSlotRegistry constant, NativeSlot, NativeSlotMapping, and host on the App side, then run slot_inventory.py.

Add host containers

Add NativeSlot / OfficialSlot calls at the matching page or control position.

Add companion implementations

Register the matching SlotContribution / PageContent in the companion, keep NativeSlot aligned with the JS registration, then scan again.

Wire interaction capabilities

When RPC is needed, confirm PluginRpcHost is injected by SlotBridgeHost and the App has set NativeHost.rpcHandler.

Confirm coverage is complete

Trust --check, slot_inventory.py, and SlotCoverageTest; screenshots only serve visual acceptance.

06Publishing and store discovery#

Publishing JS/APK, tags and topics, and how the store index takes effect.

1 · Repo topic

dsh-mobile-plugin

The store index searches repos by topic:dsh-mobile-plugin. Add it under About → Topics on the repo page, or with gh api -X PUT repos/<owner>/<repo>/topics -f 'names[]=dsh-mobile-plugin'.

2 · Release tag

v0.17.18

The store reads the latest release, and the tag anchors it. Use git tag -a v0.17.18 + gh release create v0.17.18 ...; do not publish it as a prerelease.

3 · APK asset

At least one .apk

The Release must include the companion APK, with an asset name ending in .apk; without an asset the detail page shows "No APK in the latest Release".

Propagation

About 30 minutes

A scheduled Action in the SDK repo generates docs/store/index.json; the App reads only the index and never calls the GitHub API directly. A new Release reaches the store within about 30 minutes.

# 1) Repo topic (store discovery)
gh api -X PUT repos/<owner>/<repo>/topics \
  -f 'names[]=dsh-plugin' -f 'names[]=dsh-mobile-plugin' -f 'names[]=android'

# 2) Tag and push it (the store reads the latest release)
git tag -a v0.17.18 -m "companion 0.17.18"
git push origin v0.17.18

# 3) Create the Release on that tag and upload the APK asset
gh release create v0.17.18 dsh-plugin-<name>-companion-0.17.18.apk \
  --title "v0.17.18" --notes "Companion APK for <js-package> 0.17.18"
Not in the store? Check in order

① Is the repo public and did the topic save; ② is the Release the latest (not a prerelease); ③ is there a .apk asset; ④ has the index refreshed (up to about 30 minutes); ⑤ a README-only or JS-only push never reaches the store.

07UI design guideline#

Sizing, hierarchy, and acceptance for DshPanel / DshButton and the other components.

Page skeleton

16dp / 8dp / 11sp

16dp page margins; 8dp between panels; section headers 11sp in the tertiary text color; panels with 16dp radius, a 0.5dp hairline border, and 16dp padding.

Panels

DshPanel + DshPanelRow

One panel holds a single kind of setting; rows are 44dp tall; only tappable rows get a pressed state; put descriptions in subtitle or DshPanelCaption.

Buttons

DshButton's four tiers

One PRIMARY per screen; SECONDARY for cancel or peer actions; GHOST for inline text actions; DANGER for delete, sign-out, and revoking access — always with a confirmation.

Controls

Switches / inputs / dialogs

DshSwitchRow, DshTextField, and DshDialog already encapsulate sizing and theme; disabled state is uniformly 40% opacity — never recolor it yourself.

ComponentPurposeConstraint
DshPanel / DshPanelRowSettings groups and rows16dp radius, 44dp row height
DshButtonSave / cancel / dangerous actionsOne PRIMARY per screen; 40dp height
DshSwitchRowToggle settings36×20 track, 16dp thumb
DshTextFieldText input12dp radius; placeholder required
DshChipStatus/category labelNot clickable
DshDialogConfirmation / dangerous actionsAt most two buttons; use DANGER for dangerous confirmation
